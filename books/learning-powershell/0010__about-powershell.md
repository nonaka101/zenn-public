## Windows PowerShell とは

Windows PowerShell は、Windows に標準で備わっている**コマンド実行環境**であり、あわせてオブジェクト指向の**スクリプト言語**でもあります。

:::message

PowerShell には、`Windows PowerShell` と `PowerShell` の 2 種類あります。本書で扱う PowerShell は、特段の指定がなければ基本的に `Windows PowerShell` の方を指しているものとします。

:::

Windows での一般的なコンソールとして「コマンドプロンプト」がありますが、それと比べると PowerShell は下記の特徴があります。

### 従来のコマンドラインツールも利用できる

PowerShell 登場前は コマンドプロンプト（`cmd.exe`）を使ったバッチ処理や、VBScript などがありました。

PowerShell では、従来のコマンドプロンプトで使用していた多くの外部コマンドも実行できます。

```ps1
# PowerShellでは、コマンドレットに加えて従来の外部コマンドも実行できる

Test-Connection google.com  # PowerShell コマンドレット

ping google.com             # コマンドプロンプト
```

:::message

なお、`Test-Connection` と `ping.exe` は目的が似ているだけで、引数、出力形式、機能など細かいところは異なってきます。

:::

### Windows の様々な設定や管理操作を実行できる

PowerShell では Windows 上の各種機能やレジストリなど、設定への深いアクセスが可能です。

また Microsoft 製品と親和性が強く、様々な管理機能を扱えます。

組織での運用の場合は、`Microsoft Graph PowerShell SDK` や各サービスの管理モジュールを使用することで、[Microsoft 365 管理センター](https://learn.microsoft.com/ja-jp/microsoft-365/admin/?view=o365-worldwide)で行っている様々な管理操作を実行することもできます。

### `.NET` を活用できる

PowerShell の利点の 1 つは、`.NET` のクラスやメソッドを利用できることです。

- 例：計算メソッド（`[Math]::Round(1.23456, 2) # -> 1.23`）
- 例：フォーム呼び出し（`[System.Windows.Forms]`）

### 出力がオブジェクト

PowerShell が強力であり 他と大きく異なる点の 1 つが、**オブジェクトを中心とした設計**であることです。

一般的なシェル言語（例：`bash`）では UNIX 型のアプローチ（テキストでの入出力をパイプで経由させる）が主となっています。しかし PowerShell は それとは異なり、**オブジェクト**（構造化されたデータ）でデータを受け渡すことができます。

データはオブジェクトの型に応じて 様々なメソッドやプロパティで管理されており、PowerShell においては下記のような処理を頻繁に使います。

- オブジェクトを別の処理への入力として利用する
- コマンドの出力をパイプ（`|`）で別のコマンドへ渡して利用する

### その他の特徴

その他にも、様々な特徴があります。

- 繰り返し作業をスクリプトとして保存する
- よく使う処理を切り出し、モジュール化することで再利用を容易に
- リモート接続することで、複数の端末や利用者を対象に一括処理できる
- レジストリなど様々なデータ構造に対し、ファイルシステムでの階層的データ構造として処理ができる（※[プロバイダ](https://learn.microsoft.com/ja-jp/powershell/scripting/developer/provider/windows-powershell-provider-overview)という考え方）
- 自動での型推論（※下記）

:::message

他のプログラミング言語でもよく見かけますが、PowerShell は静的に型を定義する必要はありません。

```ps1
$a = 1 + 2    # -> 3（System.Int32）
$a = "1" + 2  # -> 12（System.String）
```

変数は、型を明示しない限り特定の型に制約されません。また、上記のように 演算や代入の状況に応じて暗黙の型変換が行われることがあります。

:::

## PowerShell で操作できること

ここでは「PowerShell を **どんなことに利用できるか**」について、例示してみます。

### Windows 上の基本的な操作

まず簡単なところでは、**ファイルシステムに関する一般的な操作**ができます。

- ファイルやフォルダの作成
- ファイルのコピー、移動、削除
- フォルダ一覧の取得
- テキストファイルの読み書き
- CSV ファイルの読み込み、出力

:::message

このあたりは、一般的なシェル言語でもおなじみの操作になります。

:::

### システム管理者としての操作

PowerShell が持つ強みとしては、**各種のシステム管理作業を自動化しやすい**ことです。組織内で運用している多数の機器に対し、一括した処理を行うことができます。

また Microsoft 製品に関する管理操作にも強いです。Windows Server だけでなく、Microsoft 365 管理センターで行っているような作業も扱うことができます。

https://www.microsoft.com/ja-jp/area/biz/smb/column-microsoft-365-admin-center

他にも様々なことが可能ですが、ここではその代表例を取り上げてみます。

- 仮想マシン（**Hyper-V**）の管理
  - 例：仮想マシンに関する一連の操作（構成、作成、起動、停止、削除など）
- **Exchange Server** 関係（メール環境の運用と管理）
  - 例：メール環境操作（メールボックス、受信者、アクセス許可など）
- **SQL Server** の管理
  - 例：データベースに関する一連の操作
- **システムサービス**の操作
  - 例：サービスの確認、開始から停止までの一連の操作
- **ネットワーク設定・管理**
  - 例：ネットワークアダブタの操作・管理（TCP/IP, DNS サーバ, DHCP クライアント の構成）
  - 例：Windows ファイアウォール構成
- **ディスクとファイル管理**
  - 例：ディスク、パーティションに関する操作
  - 例：ファイルシステム関係の操作
  - 例：セキュリティ管理（アクセス権や所有権）
  - 例：共有フォルダ管理
- **レジストリ**操作
  - 例：レジストリに関する一連の操作
- **リモート接続**を使って機器を遠隔操作
  - 例：機器名から OS バージョン、ディスクの使用状況からインストール済みソフトウェアなど、**ハードウェアおよびソフトウェアの諸情報を収集**
  - 例：更新プログラムや適用状況の確認
  - 例：イベントログの収集（Windows イベントログなど）
- **ActiveDirectory** の管理
  - 例：ユーザーアカウント、グループ、OU（組織単位）などの管理
  - 例：アカウントの有効化・無効化、パスワードリセット
- **Microsoft 365** 管理センター上での操作
  - 例：ライセンスの割り当て状況、利用可能残数の確認
  - 例：メールボックス設定の確認
  - 例：Teams での設定確認・変更（例：チーム作成）
  - 例：共有メールボックスや配布リストの管理
  - 例：Exchange Online に関する設定確認（メールボックス関係 など）

## 企業のシステム管理者にとっての PowerShell とは

PowerShell は誰でも使えるものではありますが、最も有効に（かつ強力に）扱えるのは**企業や組織のシステム管理者**です。

前述した一連の操作というのは、GUI (画面操作)でも実現することは可能です。

しかし下記の事由より、PowerShell を使った 自動化を行うことを（可能であれば）取り入れるべきだと考えております。

### 作業の自動化

システム管理者として、大量の作業を自動化させることは非常に重要です。

ここでは作業を自動化させることの一般的な考えから、PowerShell 独自の機能についても簡単に説明します。

#### 大量処理における人的ミスの削減

（数件の処理ならともかく）件数が数十件から数百件に増えた場合、リソース（工数、人員）や人的ミスの観点から 手作業は現実的ではありません。

組織として運用している以上、同じような作業を長期間行うことは十分に想定され、それを前提に考えるべきです。

#### 特定の条件をトリガーとした自動実行

「定期的に」「何かのタイミングで」行う作業を *人力で* やっている場合、作業漏れの可能性が生じます。

PowerShell でスクリプトファイルを作成しておくと、例えば下記のようなことが可能です。

- スタートアップと組み合わせ、**起動時**に実行
- タスクスケジューラと組み合わせ、**定期的**に実行
- その他何らかのシステム、スクリプトと組み合わせ、**特定のタイミングで**実行

#### 教育コストの低減

新人に教育したり 他の担当者へ引き継ぐことを考える際、GUI 上で ActiveDirectory や Microsoft 365 管理センターの作業工程を逐一説明するのは大変です。

例えば 人によって教育レベルが異なりますし、画面の UI が変わった際には手順や用意しているマニュアルを再確認する必要が出てきます。

「シェルによる操作も 慣れていない人にはとっつきにくい」という点は否定しません。ただ、場合によっては「複数の画面上での操作説明を教えるのでなく、**必要な情報を揃えてスクリプトを実行する**」方が単純になるケースもあるのではと私は考えています。

:::message

「コードが何を行っているか」を把握していなければ、何かしらのイレギュラーに対応できなくなることを考えると、この方法は一長一短です。

ただし昨今は 生成 AI の精度が向上してきたのもあり、スクリプトファイルのコードを AI に提示して解説や改修案を得る やり方も取れるようになってきています。

しかし個人的には「それでも現在は、最終的には人が内容を検証すべき」だと思っています。特に組織での運用を踏まえると、「その責任を誰が負うか？」というのは非常に重要です。

:::

#### 様々な環境下で自動的に処理

PowerShell では、処理を**バックグラウンドジョブとして実行可能**です。これにより他の処理と並行して何かしらの処理を行えます。

またスクリプトは**リモート接続した機器上で実行が可能**です。離れた場所にある機器へリモート接続し、複数のコンピュータを同時に管理することができます。

そして PowerShell の特徴として、**DSC**（ *Desired State Configuration* ）という仕組みがあります。

##### DSC（*Desired State Configuration*）

:::message

DSC には複数の定義がありますが、本書で Windows PowerShell で扱える `PowerShell DSC` という構成管理機能に関する説明となります。

:::

https://learn.microsoft.com/ja-jp/powershell/dsc/overview

直訳すると「望ましい構成状態」となりますが、これは**システムの望ましい構成を宣言し、その状態を検査・適用するための仕組み**です。

- サーバにインストールされている*べき*ソフトウェアが何であるか
- 稼働時に動いておく*べき*サービスが何か
- 適用状態にある*べき*セキュリティポリシーは何か

こうした「望ましいとされる」一連の状態を監視し、適宜その構成を維持しようと自動的に動いてくれる仕組みが PowerShell では実装できます。

### 記録と再利用

作業の自動化と同じくらい重要な要素として、**記録**と**再利用**が挙げられます。

#### 記録

他のシェル言語同様 PowerShell も、処理内容をログファイルとして出力し、証跡として保存することができます。

また、PowerShell は出力用に様々なコマンドレットが用意されています。外部出力については 単純なテキストデータにとどまらず、**構造化されたデータ（CSV や HTML など）としても出力が可能**です。

| 用途 | コマンド例 |
| :--- | :--- |
| ターミナル上への出力 | `Format-*` 系のコマンドレット |
| テーブルビューでの閲覧 | `Out-GridView` |
| ファイルへの出力 | `Out-File`, `Export-Csv`, `ConvertTo-Json` など |
| HTML レポートの作成 | `ConvertTo-Html` |

こうした機能を使って、人が見やすいように（または生成 AI や Power Apps 系に活用できるよう）整形することができます。

#### 再利用

一度作成したスクリプトファイルは、定期的な実行に役立つだけでなく、再利用に回すこともできます。また `git` などのバージョン管理システムと組み合わせることで、コードの管理も容易になります。

- 似たような業務が発生した際、既存のコードを再利用する
- 処理の変更点管理は、コード内のコメントや、バージョン管理システムで行う
- 変更点をレビューしやすい

## PowerShell を扱う上で注意すべきこと

ここまで PowerShell の利便性について中心に話してきました。一方で PowerShell は、**高い利便性と強力な機能を持つが故に**、その扱いには十分な注意が必要です。

ここでは、その部分に焦点を当て説明していきます。

### 操作によっては管理者権限が必要となる

PowerShell 自体は一般ユーザー権限でも利用できますが、システム設定の変更など **一部の操作には管理者権限が必要です**。

例えば下記のような処理には管理者権限が必要となります。

- システム設定の変更
- サービス管理
- イベントログの詳細取得
- レジストリ変更
- ユーザー管理
- サーバー構成変更

:::message

また、ActiveDirectory を操作するには、ActiveDirectory モジュールなどの管理ツールと、対象環境に対する適切な権限が必要となります。

他にも Microsoft 365 系の操作を行う場合は、作業者に[適切な管理者 Role](https://learn.microsoft.com/ja-jp/microsoft-365/admin/add-users/about-admin-roles) が割り振られている必要があります。

:::

### 警告なしに重大な操作ができる場合がある

権限が高いということは、便利であると同時に危険でもあります。

GUI 上の管理ツールを使った操作の場合、重要な操作の前に確認ダイアログが表示され「本当に実行しますか？」と聞かれることがあります。

しかし PowerShell での自動化を考えると、こうした都度の確認は邪魔になってきます。そのため下記のような重要操作を PowerShell 上で行った場合、（コマンドの書き方によっては）**確認なく次々に処理を進めること**ができてしまいます。

- ファイル削除
- アカウント無効化
- 権限変更
- レジストリ変更
- メールボックス設定変更
- 大量データへの一括反映

扱う内容にもよりますが、**誤ったコマンド 1 つで多くの利用者や業務へ影響を及ぼす可能性がある**ことを、十分に認識しておかなければなりません。

### 実際に扱う際に

こうした強力な効果を持つことを学んだ上で、**実際に扱う際に心がけておくべきこと**は、下記に集約されていると私は考えています。

```txt
あなたはシステム管理者から通常の講習を受けたはずです。
これは通常、以下の3点に要約されます:

   #1) 他人のプライバシーを尊重すること。
   #2) タイプする前に考えること。
   #3) 大いなる力には大いなる責任が伴うこと。
```

上記は 一部の UNIX 系環境で `sudo` を初めて実行した際に表示されるものですが、PowerShell にも同じことが言えます。

その上で これから学んでいく際には、私は下記の点に気をつけるべきだと思います。

#### コマンドの意味を調べずに実行してはならない

インターネット上には多くの PowerShell のサンプルコードが公開されています。さらに昨今では 生成 AI の力を借りて、業務効率化のコードを容易に生成できるようになりました。

しかし、それを *そのまま* 組織内の環境で実行するのは危険な行為です。業務として PowerShell を使う場合、**理解してから実行する** ことが原則だと思われます。

- そのコマンドは**何を**対象にするのか
- **参照**だけなのか、**変更**まで行うのか
- **条件指定**や**対象範囲**は適切か
- 実行後に**元の状態に戻せるか**
- 自社環境にそのまま適用して問題ないか

#### 説明責任を持つということ

では、「ネット上にあるサンプルコードが使えそうだと考えた場合」や「生成 AI を使って業務効率化のコードを作った場合」には、どうすればいいのでしょうか？

私は、**自身が説明責任を負ったものとして振る舞うべきだ**と思っています。そして自身の責任を果たすために、下記の行為が重要となってきます。

1. 内容を読んで、理解する
2. 検証を行う
   - 対象を限定してみる
   - 参照系のコマンドで事前に確認する
   - 検証環境やテスト対象を用いて実行してみる
3. 実行結果を確認する
4. 本番へ展開する

このように「事前に何をしているのかを把握」し「影響範囲を小さくしたうえでの検証やテストをしていく」ことが、PowerShell に限らず管理作業全般に通じる 重要な考え方 だと思っています。

:::message

PowerShell には `-WhatIf` 共通パラメータなどを使ったテスト実行（実際に処理はせず、どのようなことが行われるかを表示）など、検証に利用できる機能がいくつか用意されています。

:::

##### 余談

余談になりますが この「説明責任」について 私は、PowerShell に限らず**様々な場面でも**当てはまることだと思っています。

Web 上にある情報を取り入れる場合、参考にはできますが、運用に持っていくには誰かが責任を負わなければなりません。

そして生成 AI を使って何かしらの作業をするにしても、その責任は生成 AI 自体に押し付けることはできません。

例えば Microsoft の *Copilot* は英語で**副操縦士**を意味しています。そこから考えるに、責任を負うべき**機長**（ *Pilot* ）とは**生成 AI を扱う当人**になると私は考えています。

https://news.microsoft.com/ja-jp/2023/03/17/230317-introducing-microsoft-365-copilot-your-copilot-for-work/

> マイクロソフトが新たに提供する仕事の副操縦士は、最も普遍的なインターフェースである自然言語を通じて、人々にさらなる主体性を与え、テクノロジをよりアクセスしやすいものにします。
>
> Copilot では、いつでもあなたがコントロールできます。何を残すか、何を修正するか、何を捨てるかを決めるのはあなたです。
